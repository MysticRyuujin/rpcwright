# hivechain: the test chain generator (and how to bump the chain's fork)

The fixed chain that every fixture is generated against does not live in
execution-apis — it is generated by **`hivechain`**, a tool in the **hive repo**
(`$HIVE/cmd/hivechain`), driven by `$EXECapis/tools/mkchain.sh`. Bumping the test
chain to a new fork (e.g. prague → osaka+bpo) is a **two-repo change**: hivechain
first, then execution-apis.

## The data flow (who produces / consumes what)

```
$HIVE/cmd/hivechain  ──(mkchain.sh)──▶  $EXECapis/tools/chain/
    genesis.json chain.rlp forkenv.json headfcu.json accounts.json txinfo.json headstate.json
        │
        ├─▶ make fill: rpctestgen inits geth from tools/chain, runs generators,
        │   and COPIES genesis.json + chain.rlp + forkenv.json + headfcu.json
        │   into tests/ (cmd/rpctestgen/generate.go). Never hand-edit the tests/
        │   copies — they are overwritten on every fill.
        │
        └─▶ hive rpc-compat: loads tests/forkenv.json and passes each key to the
            client container as HIVE_* env vars; the client's mapper.jq turns
            them into that client's genesis/config. headfcu.json is the
            engine_forkchoiceUpdatedV3 call that sets the client's head.
```

`accounts.json` (pre-funded senders) and `txinfo.json` (per-mod tx tags like
`tx-eip7702.account`) feed the testgen helpers `GetSender`, `FindTransaction`,
and `t.chain.txinfo`.

## mkchain.sh knobs and the fork-placement math

```sh
./hivechain generate -outdir chain/ -length 54 -tx-count 4 -tx-interval 1 \
    -fork-interval 3 -lastfork bpo2 \
    -disable-txmods tx-largereceipt \
    -outputs genesis,chain,forkenv,headstate,txinfo,accounts,headfcu
```

- Forks activate every `-fork-interval` blocks starting at genesis, in the
  hard-coded mainnet order in `genesis.go` (`preMergeForkNames` +
  `posForkNames`). Post-merge forks are timestamp-based; block time is 10s
  (hard-coded in `core.GenerateChain`), so fork at block N ⇒ timestamp N*10.
- **`-length` must be ≥ (numForks−1) × forkInterval** or the trailing forks all
  pile up on the last block. 19 forks (13 pre-merge + shanghai…bpo2) × 3 = last
  fork at block 54. The convention is head == last-fork activation block.
- `-lastfork` truncates the fork list; the fork must exist in `posForkNames`.

## Locate blocks before and after the target fork

Read the schedule from `tests/genesis.json` and the generated block timestamps.
Do not assume every fork activates at genesis or that every fork is present.
The bpo2 example uses a three-block interval and reaches block 54:

| fork | activates at block | pre-fork range |
|---|---|---|
| eip150 / eip155+158 | 3 / 6 | 0-2 / 3-5 |
| byzantium / constantinople / petersburg | 9 / 12 / 15 | |
| istanbul / muirGlacier | 18 / 21 | |
| **berlin** (EIP-2929/2930) | **24** | **6-23** (EIP-155 active, so signatures validate) |
| london | 27 | 24-26 |
| arrowGlacier / grayGlacier / mergeNetsplit | 30 / 33 / 36 | |
| shanghai (t=390) | 39 | |
| **cancun** (t=420, EIP-4844) | **42** | 39-41 |
| **prague** (t=450, EIP-7702) | **45** | 42-44 |
| osaka / bpo1 / bpo2 (t=480/510/540) | 48 / 51 / 54 | |

Timestamp forks: block N has timestamp N*10. To exercise "field X at a block before
its fork," pass the block **number** as the block param (`"0x14"` = block 20 is
pre-Berlin, pre-Cancun and pre-Prague at once, with EIP-155 active). Genesis-alloc
contracts (e.g. the storage contract at `0x7dcd17433742f4c0ca53122ab541d0ba67fc27df`,
called with input `0x010203040506`) and `accounts.json` senders exist at every
block, so no tx-mod lookup is needed. Verify the selected client's imported head
and historical state before interpreting a missing result.

### Surveying raw client behavior with hive (no expected value needed)

For a client behavior survey, use temporary `.io` files in an isolated simulator
test directory with an
impossible `<<` line (e.g. `"result":"SURVEY_PLACEHOLDER"`), give them a shared name
prefix, and run `--sim.limit "rpc-compat/<prefix>"`. Every case "fails" — that is the
point; the raw answers are in the per-test log. The request/response pairs are NOT in
the simulator log; they live in `workspace/logs/details/<sim-id>-0.log`, addressed by
byte offsets from the results JSON (`summaryResult.log.{begin,end}`), as `>> ` / `<< `
lines:

```sh
cd $HIVE; F=$(ls -t workspace/logs/*-*.json | head -1)
D=workspace/logs/details/$(basename $(jq -r .simLog $F) .log | sed "s/-simulator-/-/")-0.log
jq -r '.testCases|to_entries[]|select(.value.name|test("<prefix>"))|"\(.value.name)\t\(.value.summaryResult.log.begin)\t\(.value.summaryResult.log.end)"' $F \
| sort | while IFS=$'\t' read -r name b e; do
  printf '%s\t%s\n' "$name" "$(tail -c +$((b+1)) $D | head -c $((e-b)) | sed 's/\x1b\[[0-9;]*m//g' | grep -a -m1 '^<<' | sed 's/^<< *//')"
done
```

Use runtime results to confirm behavior inferred from source. Record client
revisions and configuration with the responses. Keep survey fixtures outside the
committed corpus and remove them from subsequent conformance runs.

Past ethrex surveys report missing state at early blocks while genesis queries
succeed. Recheck this on the selected revision. A genesis query is a separate
data point; different fork and signature rules can prevent a direct comparison.

## Bumping the chain to a new fork — the recipe

1. **hivechain (hive repo):** a new fork needs BOTH ends:
   - `genesis.go`: fork name in `posForkNames` + a `case` setting
     `chaincfg.<Fork>Time` and `BlobScheduleConfig.<Fork>` (geth's
     `params.Default<Fork>BlobConfig`).
   - `output_forkenv.go`: `setTime("HIVE_<FORK>_TIMESTAMP", …)` + the
     `HIVE_<FORK>_BLOB_{TARGET,MAX,BASE_FEE_UPDATE_FRACTION}` vars.
2. **Check every client mapper consumes the vars**: `grep -l "HIVE_<FORK>" 
   $HIVE/clients/*/mapper.jq`. Mappers often gain fork support before hivechain
   emits it (osaka sat consumed-but-never-emitted for months).
3. **execution-apis:** build hivechain (`go build ./cmd/hivechain` in hive),
   drop the binary in `tools/`, update `mkchain.sh` (`-lastfork`, `-length`),
   run it, then bump `tools/go.mod` geth (see below), fix generators, `make
   fill`, `./tools/speccheck`, hive run.

Precedent PRs: prague bump execution-apis #612; osaka+bpo bump (this playbook).

## Gotchas (each cost real debugging time)

- **The forkenv emission gap is silent.** If `output_forkenv.go` doesn't emit a
  fork the genesis has, geth-family clients (which read genesis.json directly in
  rpctestgen) run the new fork while hive clients (built from forkenv via
  mapper.jq) run the OLD config — every fixture generated at the new-fork head
  fails in hive with no hint why. Verify `jq 'keys' tests/forkenv.json` shows
  the new fork before blaming a client.
- **`make fill` builds the reference geth FROM `tools/go.mod`** (`make geth`).
  Bumping go.mod is not hygiene — it selects the reference client's behavior.
  Example: geth #35191 (2026-06) rejects v0 blob sidecars unconditionally
  (`unexpected sidecar version, want: 1, got: 0`), so post-osaka fills need both
  the go.mod bump and generators that build v1 sidecars
  (`kzg4844.ComputeCellProofs` + `types.NewBlobTxSidecar(types.BlobSidecarVersion1, …)`).
  chain.rlp itself is wrapper-agnostic — hivechain strips sidecars from blocks
  (`WithoutBlobTxSidecar`), so only `eth_sendRawTransaction`-style generators care.
- **hivechain master accrues new tx mods; regeneration changes the tx
  population, not just the head.** New mods (e.g. `modLargeReceipt`, which sends
  zero-value empty-data legacy txs at a predeployed contract) can shadow what a
  loose `FindTransaction` matcher meant to find. Symptom: a generator that
  "traces a legacy EOA-to-EOA transfer" suddenly gets structLogs — the matcher
  grabbed a contract poke. Tighten matchers (e.g. require `tx.Value().Sign() > 0`)
  rather than reordering the chain.
- **A mod can blow up fixture size — and the rpc-compat loader.**
  `tx-largereceipt` deliberately builds a block with >10 MB of receipt logs (for
  hive's own stress suites). Filled through `eth_getLogs/no-topics` it produced a
  **21 MB single-line fixture**, and rpc-compat's `.io` loader (bufio.Scanner,
  1 MiB buffer in `testload.go`) fails the whole run at load time:
  `failed to load tests: invalid test no-topics.io: bufio.Scanner: token too
  long` — reported under the *client launch* test even though the client started
  fine. Exclude bulk mods with `-disable-txmods tx-largereceipt` (flag added for
  exactly this; mods have no other opt-out — all registered mods always run).
  After any regen: `du -sh tests/` and check the longest line
  (`awk '{print length}' tests/**/*.io | sort -rn | head -1`) stays well under
  1 MiB.
- **A new fork can turn a test's scratch address into a precompile.** Osaka's
  P256VERIFY landed at 0x100; a simulateV1 fixture forwarding ETH there via
  Solidity `transfer()` (2300 gas stipend) started reverting `Failed to send
  Ether` because the precompile's base cost exceeds the stipend. Keep
  state-override/forward targets out of plausible precompile ranges (0x01–0x1f,
  0x100+). Check scratch addresses against the selected fork's precompile set;
  no address convention guarantees compatibility with future forks.
- **Don't commit the hivechain binary** (~17 MB). `tools/.gitignore` covers the
  other built binaries; make sure `/hivechain` is listed too.
- **Debugging a generator failure? Run geth on the chain by hand** — faster than
  round-tripping through make fill:
  ```sh
  cd $EXECapis/tools
  debug_datadir=$(mktemp -d)
  ./geth --datadir "$debug_datadir" --state.scheme=hash init chain/genesis.json
  ./geth --datadir "$debug_datadir" --state.scheme=hash --gcmode archive import chain/chain.rlp
  ./geth --datadir "$debug_datadir" --state.scheme=hash --gcmode archive --ipcdisable \
    --http --http.api eth,debug,net,txpool --http.port 18545 \
    --port 30310 --authrpc.port 18551 --nodiscover --maxpeers 0
  ```
  Use non-default ports — a dev box often has a real node on 8545/30303, and
  querying the wrong one produces mainnet-looking numbers that derail debugging.
- **Fixture diffs after a chain bump are total.** Every hash/number/fee changes;
  the diff is unreviewable line-by-line. Review instead: fill exits 0 (all
  generators' internal assertions passed), speccheck passes, spot-check
  fork-sensitive fixtures (`eth_config`, `eth_blobBaseFee`, `send-blob-tx`
  wrapper bytes), and let the hive run be the behavioral check.
- **Attribute cross-client failures with an A/B baseline, not the daily runs.**
  Comparing your run against hive.ethpandaops.io dailies conflates three drifts:
  your chain change, client-image drift (today's `master`/`main-latest` vs the
  daily's), and infra drift (the daily's sim may embed older fixtures or an older
  hive). The clean discriminator: run the SAME client images against the OLD
  fixtures (`git worktree add /tmp/main main && rsync main-worktree/tests/ →
  sim tests/`), then diff the two failure sets. Failures present in both = client
  drift, not your bump. (Osaka bump verdict: geth master 233/233; every
  erigon/nethermind/reth failure reproduced on old fixtures too — zero caused by
  the bump.)
